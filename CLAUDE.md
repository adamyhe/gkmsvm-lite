## Conventions

- Python >=3.10, NumPy, Numba >=0.57, scikit-learn, tqdm. CuPy >=12 optional (`[gpu]` extra). MLX >=0.10 optional (`[mlx]` extra)
- Array format: inputs are `[batch, 4, length]` one-hot DNA (channel order A=0/C=1/G=2/T=3, any dtype), DNA strings, or `[batch, length]` uint8 base codes. Internally everything is base codes (A=0/C=1/G=2/T=3): `svm.as_batch` (every scoring/ISM/explain entry), `train._to_codes` and `pack` convert with `codec.to_codes` (argmax, so N, an all-zero column, becomes A, as every kernel reads it), strings go straight to codes (`codec.encode_codes`), and `GkmSVM.support_sequences` is `[S, L]` uint8 (one-hot SVs given to the constructor, e.g. old npz files, are converted). One-hot appears only at the edges: GkmExplain importance (`codec.codes_to_one_hot` times the hypothetical scores) and the CLI's saved sequence arrays. deltaSVM's RC strand is `3 - codes[::-1]`, so N reads T there, as in the gkm-SVM kernels
- Output: `[batch, 1]` margin scores. Precision doesn't follow the input: scores, ISM, attributions, Gram matrices, coefficients, cached norms and deltaSVM weights are float64 on CPU and CUDA, float32 on MLX (`backend.float_dtype`; `DeviceModel._FLOAT_ARRAYS` keep that across device moves, so moving to MLX rounds them). `one_hot_encode` (float32 by default) and `extract_loci` (int8) are the user-facing I/O; the CLI reads genome windows through `fasta.loci_sequences` straight to codes
- Arrays are numpy.ndarray (CPU), cupy.ndarray (NVIDIA GPU), or mlx.core.array (Apple GPU)
- `model.cuda()` / `model.mlx()` / `model.cpu()` moves arrays between devices (`backend.DeviceModel`, shared by `GkmSVM` and `DeltaSVM`)
- Kernel normalization on by default, RC equivalence on by default
- Score = `Σ coef_i × K(x, sv_i) + bias` where `bias = -rho` (LS-GKM), or 0 (classic/R gkmSVM, whose files hold no bias)
- `resolve_kernel_type()` maps aliases and integers to canonical internal names
- Kernel modes: `-t 0` gkm_cnt/direct, `-t 1` gkm_estfull/estimated_full, `-t 2` gkm_esttrunc/estimated (default), `-t 3` gkmrbf/rbf, `-t 4` wgkm/weighted, `-t 5` wgkmrbf/weighted_rbf, `-t 6` gkm_cnt_rbf/direct_rbf (RBF on `-t 0`; kundajelab fork only; oracle `tests/fixtures/lsgkm_wgkm_t6*`)
- ISM: `ism(model, x, batch_size=N)` → `[B, 4, L]` score deltas (window-delta optimization)
- GkmExplain: `gkmexplain(model, x, mode=..., batch_size=50)` → `[B, 4, L]` attribution scores, every kernel type (`-t 4/5`: each window pair's contributions times w_i(x) w_j(sv); V and the index entries carry the SV windows' weights, every path scales query window i by w_i). For `-t 3`/`-t 5`, as lsgkm does, each SV's contributions scale by (exp(γ(K−1)) − exp(−γ))/K of its normalized base kernel value K (0 when K <= 0), so importance sums to score − bias − exp(−γ)·Σcoef. On MLX the l-mer path and the per-SV kernel run in Metal (`_explain_lmer_metal`, `_explain_sv_metal`) and the explain table on CPU, from a CPU copy of the model (cached in `_sv_cache`; the `use_*` flags are copied on every call); the result is NumPy float64 either way, as `mutation_impact` returns NumPy on every device. Every path accumulates in float64 and returns the input's dtype. Modes (string or legacy int):
  - `"importance"` (0) — hypothetical × one-hot, N counted as A (it packs as A; as in lsgkm). Sum = score - bias (completeness axiom). For visualization.
  - `"hypothetical"` (1) — all 4 bases. For TF-MoDISco.
  - `"perturbation"` (2) — discrete kernel-value Δ per mutation (lsgkm C mode 4: `perturbation_eff=1` over every pair with up to d+1 mismatches, i.e. every pair a substitution changes; mode 3 leaves out the d+1 pairs). Each SV's ΔK is divided by the reference's norm (not the mutant's), and RBF models spread exp(γ(K−1)) − exp(−γ) proportionally as in the other modes, so it approximates score(mutant) − score(ref) rather than equaling it, as lsgkm's does. Oracle: `tests/fixtures/*.explain4.txt.gz`.
- Oracles for every mode and kernel type (`-t 0`-`-t 5`): `tests/fixtures/*.explain{0,1,4,5}.txt.gz`, kundajelab lsgkm fork's gkmexplain (`benchmarks/dev/lsgkm_wgkm_fixtures.py --explain-bin`; the fork rejects a `norc` line, so the script drops it).
- Mutation impact: `mutation_impact(model, ref, alt)` = lsgkm `gkmexplain -m 5`, the paper's dsQTL VEP score. `score_variants(method="gkmexplain")` calls it. Normalizes ΔK by the ref norm only, so without RBF it is linear in the SVs and reads the l-mer table when it applies: (T(alt) − T(ref)) / sqrt(K(ref, ref)), T the table sum (`_table_raw`; dsQTL `-t 2` model, 500 variants: 7.0 s -> 0.01 s on CPU); RBF distributes `exp(γ(K-1)) - exp(-γ)` proportionally to ΔK/K, through the l-mer index in one fused CPU pass per variant (`LmerIndex.impact`: K(ref) and ΔK in two length-S buffers, ΔK visiting only the window slots where the alleles differ, so a SNP costs about one query; dsQTL `-t 3`, 500 variants: 9.8 -> 5.1 s), which MLX also takes when its index queries on CPU (`LmerIndex.queries_on_device`). Not equal to ISM. Oracle: `tests/fixtures/lsgkm_mode5_*`.
- RBF (`-t 3`, `-t 5`): `K = exp(γ(K_norm - 1))` on the normalized base kernel, matching lsgkm.
- `to_deltasvm(query_norm=True)` makes each weight = gkmpredict on that l-mer (how lsgkm deltaSVM weights are built); default drops the l-mer norm.
- `batch_size` on `model()`, `score_variants()`, `ism()`, `gkmexplain()` chunks over inputs. Kernel scoring computes [rows, S] blocks of at most `GkmSVM._MAX_SCORE_BYTES`; `model.sv_chunk_size` only chunks SVs in GkmExplain. When scoring goes through the masked join (no l-mer table or index), small `batch_size` values are raised so each call fills ~256 MB of [batch, S] (`GkmSVM._min_batch_size`): every masked-join call indexes all SV windows.
- `verbose=True` on `model()`, `score_variants()`, `ism()`, `gkmexplain()` enables tqdm progress bars over input batches
- No PyTorch dependency. Gradient-based methods are incompatible — use GkmExplain or ISM
- tangermeme interop is vendored (pyfaidx for FASTA extraction)

## Key implementation details

- GkmExplain explain table (`-t 0/1/2`, `explain._build_explain_table`): a pair's weight at position k depends only on the mismatch count and the 2-bit delta d = (u ^ v)_k there, so every window's attribution A[u, d, k] = sum_v V[v] G_kd(u ^ v) is an XOR convolution over the 4^l l-mers, computed with Walsh-Hadamard transforms (H(G_kd) is H(G_0d) with digits 0 and k swapped; the 4l inverse transforms run together down A's [4^l, 4l] rows). [4^11, 4, 11] float64 = 1.4 GiB, built in ~1 s on an M4; then 0.035 ms per 300 bp sequence on CPU, agreeing with the other paths to ~1e-14. One table per mode (hypothetical/importance share one) in `model._explain_tables` (host memory, kept across device moves, dropped by `clear_caches`). `model.use_explain_table`: `"auto"` builds one when a call's rows times the per-sequence cost (`_EXPLAIN_SEQ_S`, CPU vs CUDA) exceed the estimated build time and it fits `_EXPLAIN_TABLE_BYTES` (2 GiB), or reuses one already built; True/False force it. Lookups run on CPU; results return to x's device. Not for RBF (query-dependent SV weights).
- GkmExplain attribution is linear in the SVs, so with l <= 12 and either <= `MAX_NEIGHBORS` l-mers within the cutoff or >= `_EXPLAIN_SV_WINDOWS_PER_NEIGHBOR` (6; 12 in Metal, whose per-SV kernel keeps up to ~2,900 such SVs) SV windows per neighbor (`-t 0` l=11 k=7 without d, 143,980 neighbors: ~1.5k+ 300 bp SVs) it goes through `explain._explain_lmer`: V[v] = sum_s coef_s / sqrt(K(sv, sv)) times v's occurrences in sv_s and its RC (4^l float64, cached), and each query window visits its neighborhood, adding V[v] times the alpha/kappa (or perturbation) weight to each position. Nothing per SV (3.5 ms per 300 bp sequence for ENCFF579AOX on an M4). For `-t 3` the SV weights depend on the query, so each neighbor sums them over the l-mer index's CSR entries instead (`_explain_index_cpu`; 29 ms per sequence for the dsQTL `-t 3` model). CUDA runs it in `explain_lmer` (`_explain_lmer_gpu`): 16 lanes per query window, lane k owning position k, look up 16 neighbors at once and shuffle them; each lane keeps four register sums indexed by the mask's 2-bit delta (a dynamically indexed [4, l] array spilled to local memory and was 5-7x slower). 5-14x the CPU path on a Titan Xp host for `-t 2`/`-t 3` (more with more SVs). Metal (`_EXPLAIN_LMER_METAL`) uses the same 16-lane groups with `simd_shuffle`, but Metal has no float64, so nothing sums across windows on the GPU: each window writes its four float32 sums per position to `[slices, B, W, 4, 16]` and `_fold_windows` folds them in float64 on CPU (no atomics); RBF neighbor sums over the CSR entries are compensated (Neumaier: plain float32 was 6e-6 of the largest attribution on the dsQTL `-t 3` model, compensated 3e-7). Within 6e-7 of the CPU's largest attribution on ENCFF579AOX and the dsQTL `-t 2`/`-t 3` models; on an M4 1.9-5x the CPU (ENCFF579AOX 3.5 -> 0.9 ms per sequence hypothetical, 27.6 -> 5.4 perturbation), 1.2-1.6x for `-t 3`, where the CPU index query for the RBF weights dominates (the Metal one is slower on 32k SVs: contended atomics). `model.use_lmer_index = False` forces the per-SV kernels.
- Forward pass, ISM, and GkmExplain use the packed uint32 path (XOR + popcount). Otherwise GkmExplain has one kernel per device (`_explain_cpu`, CUDA `fused_explain`) with a `perturbation` flag; it fuses normalization + coefficient multiplication + SV-dimension reduction, accumulating directly into `[B, 4, L]` result (no per-SV intermediate). Forward + RC SV windows concatenated for single kernel launch. CPU: `prange(B)` with L1-resident per-thread result arrays. GPU: float64 `atomicAdd` (CC >= 6.0). Apple GPU: custom Metal shaders via `mx.fast.metal_kernel`; GkmExplain's per-SV kernel (`_EXPLAIN_SV_METAL`) uses the l-mer path's 16-lane groups, a lane per SV window, and window partials folded in float64 on CPU (no float64 atomics), with a ballot so only lanes holding a pair within min_matches go round (16 x 300 bp vs 2,000 SVs on an M4: `-t 0` without d 1.13 s -> 0.30 s, `-t 2` 0.70 -> 0.12 s). ISM builds the packed windows covering each position (padded with `PAD_WINDOW`, which cancels in new − old) and works for every kernel type, by path: with the l-mer table, table weights over those windows (`ism._ism_table`); with the l-mer index, one fused pass per (position, sequence) adds the changed windows' hits to the reference row and reduces over SVs (`LmerIndex.mutants`: on CPU into a cache-resident length-S buffer; on CUDA/Metal one thread block per (position, sequence) scatters the hits into a [5, S] scratch slice with atomics and reduces sum_s coef_s (f(mutant) − f(ref)) in the same kernel, `_MUTANTS_BODY`; MLX runs the CPU pass above `_METAL_MUTANTS_MAX_DENSITY` (6) index entries per l-mer, where device-memory float atomics lose to the CPU: RBF ISM 4 x 300 bp 2.5x the CPU at 1.1 entries, 0.83x at 8.9, the dsQTL `-t 3` model has 18 (0.5x); splitting positions between Metal and the CPU running at once gained nothing there: each half alone 2.0 s, together 3.4 s); otherwise per-SV values in blocks of at most `_MAX_SCORE_BYTES`. Mutant norms come from `raw_diag_mutants`, which visits only the pairs touching a changed window (~4lW per mutant vs W^2) for every kernel type: numba on CPU (`_mutant_diag_numba`, `weighted._mutant_diag_weighted_numba`), and on CUDA/Metal `direct._mutant_diag_device`, one thread block per (base, position, sequence), window weights optional (32 x 300 bp at l=11: 100 ms on CPU, 11 ms in Metal on an M4, where the W^2 fallback it replaced took 320 ms and was most of ISM's time). With window weights (`-t 4/5`) the padded window sets aren't whole sequences, so `ism._slot_weights` gives each slot its window's weight ([L, l], 0 for padding): the table and `LmerIndex.mutants` scale by it, and `_ism_kernel` scores each window as a one-window row (weight `window_weights(1)`, divided out) and sums with the slot weights. `-t 4/5` mutant norms: `weighted._mutant_diag_weighted_numba`.
- Kernel interface: `kernel.base` is the kernel giving raw values (the base of an RBF kernel, else itself) and `kernel.finish(k_norm)` applies the RBF. Base kernels are `PackedGkmKernel`s: `pack(x)` gives [B, W] uint32 windows on x's device (MLX packs on CPU; N packs as A), `pack_both(x)` adds the RC windows derived from the packed forward ones, so N is T on the reverse strand as in lsgkm (packing the one-hot RC would give A on both strands and break the RC symmetry the l-mer table relies on), `raw_packed(bx, by, by_rc)` the raw kernel with the RC block in the same call (masked join, or brute force below 16 rows; when the columns hold more windows than the rows, e.g. scoring against SVs, the join indexes only the forward columns and probes with each row's RC and forward windows, `packed._with_rc_rows`, since K(x, rc(y)) = K(rc(x), y): the index build, which dominates there, halves, 1.5x at 16k-72k SVs on an M4; with more rows than columns, as in Gram panels and SMO columns, it lost (0.8x)), `raw_diag_packed(bx, bx_rc)` the self-kernel, `window_weights(W)` the [W] uint8 window weights (None except `-t 4/5`; the packed arrays passed around are whole sequences, so weights follow window positions). Gram, SMO columns, scoring, ISM and mutation impact all use this, so `-t 3`/`-t 5` get packed caches, Gram panels and batched SMO columns.
- The model caches packed SV windows, their base self-kernels and the l-mer index per device (`GkmSVM._sv_cache`, cleared on device moves); `model.clear_caches()` also drops the l-mer table. `use_lmer_index`/`use_lmer_table` are checked on every call.
- CPU kernel scoring normalizes, applies the RBF and reduces over SVs in one numba pass. Through the l-mer index it is fused with the query (`LmerIndex.reduce`: each row's hits accumulate in a cache-resident length-S buffer, never a [B, S] block); otherwise `svm._normalized_dot` reduces the raw block. `to_deltasvm` on RBF models scores only canonical l-mers (index <= RC index) and copies weights to their reverse complements, as lsgkm's nrkmers.py pipeline does.
- Min-matches skip: for esttrunc l=11 k=7 d=3, `min_matches=8`. 99.88% of window pairs skipped.
- CPU self-kernels for `-t 0`–`-t 5` (`_self_diagonal_packed_numba`, used for SV and query norms; `-t 4/5` use `weighted._self_diagonal_weighted_numba`) visit each pair of the symmetric forward and RC blocks once, four rows per pass over the columns, with branch-free table lookups; rows whose RC block isn't the reverse complement of the forward one visit every RC pair.
- CPU inner loop: Numba `@njit(parallel=True, fastmath=True)`. NVIDIA GPU inner loop: CuPy RawKernel with shared-memory caching. Apple GPU inner loop: Metal kernel with per-thread accumulation and `popcount()`.
- MLX compatibility: `get_strides()` for arrays without `.strides`, `xp.ascontiguousarray()` for `.copy()`, `to_cpu(X)[indices]` for fancy indexing. DeltaSVM auto-chunks intermediates >256 MB.
- Scoring against the SVs uses the cached l-mer index (`kernels/lmer_index.py`) for kernels with at most `MAX_NEIGHBORS` (8,192) l-mers within dmax mismatches, or `DENSE_MAX_NEIGHBORS` (32,768) when the indexed windows average >= 4 per l-mer, i.e. large SV sets (e.g. `-t 0`-`-t 6` with d <= 3, l <= 12, now that `d` applies to `-t 0`; with window weights each CSR entry also stores its window's uint8 weight, `LmerIndex.vals`). SMO columns (one query row each) keep the 8,192 cap, where large neighborhoods were 4-8x slower than the join. Masks are sorted so neighbor lookups stay local: CSR over 4^l l-mers listing the SVs containing each, built once; a query window visits its dmax-neighborhood, so a call costs nothing per SV. CPU/CUDA accumulate float64 (CUDA int32 per-level counting measured slower: the cost is the scattered atomics); Metal counts hits per distinct weight in int32 and combines on CPU (above `_METAL_MAX_LEVELS` distinct weights or `_METAL_QUERY_MAX_DENSITY` (2.5) index entries per l-mer, MLX queries on CPU: the counts' scattered atomics lose to it there, 0.52x at the dsQTL `-t 3` model's 17.8); with window weights it counts wx·vals in 64 bits, a uint32 word plus a carry word that the adding thread bumps when its `atomic_fetch_add` wraps the low word. `model.use_lmer_index = False` forces the masked join.
- `raw_packed` uses the masked-join kernel (`kernels/masked.py`) when both sides have >= 16 sequences: h(m) as a signed sum of C(l-m, j), each term an exact-match join on masked l-mer keys. `kernel.use_masked = False` forces brute force. `compute_gram`, when the l-mer index doesn't apply, then works in column panels so each column index is built once. MLX builds the index and joins in Metal, writing int32 counts that the CPU combines in float64. `-t 4`/`-t 5` use it too: each column window's weight sits next to its id (CPU float64 accumulation; the CUDA join counts in shared uint64, exact; Metal in two uint32 words with a carry, exact, the entry's weight in colseq's top 16 bits, `_METAL_COL_TILE_W` 2048 columns). Weighted brute force and self-kernels have CUDA and Metal kernels (`weighted._WEIGHTED_CUDA`, `_METAL_BRUTE_W`; Metal sums in float32 as the unweighted one).
- `to_deltasvm` reads the l-mer table when it applies, else scores all 4^l l-mers through `_score_unbatched` (RBF always keeps the query normalization; non-RBF without `query_norm` multiplies weights back by sqrt(K(u,u))). It never mutates the model.
- Prediction for `-t 0`/`-t 1`/`-t 2`/`-t 4` (l <= 12) uses an exact 4^l l-mer weight table (`lmer_table.py`, built from marginals of the SV l-mer weights; with RC, a mask and its mirror share one marginal, read at rc(u)): f(x) = sum_i wt_i w(x_i) / sqrt(K(x,x)) + b (wt_i: window weights, 1 except `-t 4`). `model.use_lmer_table`: `"auto"` (>= 500 SVs), True, False. RBF uses the kernel path.
- `compute_gram` (libsvm, Nyström) uses the l-mer index whenever it applies, the same rule as SMO columns (`lmer_index.applies(base)`), except on MLX: one index over the columns, X queried in row blocks of at most `GkmSVM._MAX_SCORE_BYTES`; a self-Gram row block computes only its columns from the diagonal on (`LmerIndex.pairwise(diag_offset=)`, CPU/CUDA: each l-mer's entries are sorted by column, so its scan runs down from the last and stops below the row), mirrored into the lower triangle. Against the masked join, -t 2 l=11 k=7 d=3 300 bp: 0.47x at 1k on CUDA, 0.72x on CPU (16 threads), even near 10k, 1.6x at 40k on both. On MLX the Metal query lost at every N (0.2-0.37x at 1k-20k on an M4; its neighbor lookups alone took longer than the whole join), so MLX Grams keep the masked join. Otherwise the self-Gram skips tiles below the diagonal; it works in column panels, and on CPU each panel's masked join computes only the columns at or above the diagonal (`masked._masked_pairwise_upper`, `raw_packed(diag_offset=)`). RBF tiles use the base kernel's packed path, then `kernel.finish`. `benchmarks/dev/gram_index_vs_masked.py` times the two.
- Training: `pos_weight` (CLI `-w`, LS-GKM's `-w`) sets the positives' C to w·C: sklearn `class_weight`, and `Cp`/`Cn` bounds in `_csmo`. `solver="auto"` uses the precomputed Gram + sklearn when the N×N float64 Gram fits in 75% of available RAM and under `max_gram_gb` (the Gram always lives in host RAM; tiles are computed on the training device); else column-cached SMO. `train.py` dispatches every solver through `_fit`, which builds the model. SMO uses WSS3 working set selection (C extension `_csmo` with Python kernel column callback), shrinking, and kernel columns cached in C — memory is O(cache_size × N) not O(N²). No Python fallback: without the extension, `solver="smo"` raises. `solver="nystrom"` uses low-rank kernel approximation for fast approximate training (fewer kernel evaluations; still a dense N×N approximate Gram, so no memory saving). `max_gram_gb` caps Gram allocation on shared compute.
- `KernelColumnCache` packs all training sequences once (through `kernel.base`). When the l-mer index applies (`-t 0`-`-t 6` with a small d-neighborhood), it indexes all training sequences once and a column is one query row (~3-6 ms on CPU for 300 bp, N=5-10k), so SMO prefetches only into empty cache slots (the first fill), then computes single requested columns. Otherwise columns are all rows against the requested columns and their RCs, so the masked join indexes only the batch, and misses prefetch up to `_SMO_PREFETCH` columns into free cache slots. Without the index, a cache smaller than N degrades to single brute-force columns once full.
- SVR (`train_gkmsvr`) takes the same solvers as SVC (`_auto_solver` picks for both). `solver="smo"` is `solver.smo_svr_solve`: LIBSVM's epsilon-SVR dual, 2N variables (sign +1 with linear term ε − z_i, −1 with ε + z_i), variable t using sequence t mod N's column, so `_csmo` caches N columns as for SVC (`csmo_solve(n, N, y, p, ...)`; SVC is n = N, p = −1, bit-identical to before). Coefficients α − α*. Oracle: lsgkm-svr's models (`test_train_oracle.py::test_svr_matches_lsgkm_svr`, both solvers).
- Sequence lengths (`docs/design/variable-length.md`): the main pipeline is fixed windows. CLI `--genome` reads BED/narrowPeak summit windows (`fasta.read_loci`/`extract_loci`), `--length` center-crops mixed FASTAs (`codec.center_crop`; default the model's SV length, 300 for training; shorter records are an error). Variable length is compatibility: `pack(x, lengths)` writes `PAD_WINDOW` past each row's windows (RC rows hold theirs first), and every kernel skips PAD explicitly (CPU: spans/counts from `direct._spans`/`_counts`; CUDA/Metal compare each window with `0xFFFFFFFFu`; one side suffices for brute force, since PAD against a real window falls below min_matches). `-t 4/5` weights are per row (`row_weights`: `[1, W]` when nothing is padded; the CUDA weighted join, index query and `fused_explain` take them with a row stride, 0 when shared). `GkmSVM.sv_lengths` (importers, npz, `save_lsgkm` trims); `model(x, lengths=)` or a list (`svm.as_batch`); shorter than l gives NaN with a warning. Every device runs padded input (`test_variable_length.py::test_*_on_device`). Training (`train_gkmsvm`/`train_gkmsvr` on lists of different lengths; `compute_gram(lengths=, y_lengths=)`, `KernelColumnCache(lengths)`, Nyström) keeps `sv_lengths`; sequences shorter than l are an error (gkmtrain silently builds a broken model). ISM, GkmExplain (`lengths=` or a list), `mutation_impact`/`score_variants` (`ref_lengths`/`alt_lengths`, indels allowed) and `DeltaSVM` (scored per length) take mixed-length queries: `[B, 4, L_max]` out, 0 past each length, NaN rows shorter than l. ISM: `_packed_mutations` keeps PAD, slot weights are `[L, 1 or B, l]`, the mutant self-kernels use each row's span. Oracles: `tests/fixtures/lsgkm_ragged_*`: gkmpredict on mixed-length queries; gkmtrain's models on `lsgkm_ragged_{pos,neg}.fa` (same SVs, coefficients to the solvers' 1e-3 tolerance, and gkmtrain's solution meets our KKT conditions to 6e-4); gkmexplain modes 0/1/4/5 on `lsgkm_ragged_query.fa` (odd lengths 31-151) for every fixture model (`*_query.explain*`).
- `scikit-learn` provides the LIBSVM C solver for both SVC and SVR via `SVC(kernel='precomputed')` / `SVR(kernel='precomputed')`. No direct `libsvm-official` dependency.

## Gotchas

- N: lsgkm encodes any non-ACGT base as A before taking the reverse complement, so N is A on the forward strand and T on the reverse one (`pack_both`), for every kernel type. Imported models' coefficients were fit with that kernel, so N is not treated as its own symbol. String inputs (CLI FASTAs, `train_gkmsvm`/`train_gkmsvr` DNA strings) accept N (`one_hot_encode(allow_n=True)`); other non-ACGT letters raise unless `allow_other=True` (`--allow-other-bases`, `allow_other_bases=`), which reads them as N, matching gkmpredict (LS-GKM reads every non-ACGT letter as A). Importers always read them as N, with a warning: the model was fit that way.
- LS-GKM defaults are `-t 2 -l 11 -k 7 -d 3`. Always pass parameters explicitly when generating oracle fixtures.
- The `d` parameter zeros weight table entries for m > d, for every kernel type including `-t 0` (LS-GKM's search visits only pairs within d mismatches; at l=11 k=7 d=3 that drops `-t 0`'s m = 4 term). Without this, scores diverge ~1.5% from `gkmpredict`. `DirectGkmKernel(d=None)` (a `-t 0` model with no `d` in its params, e.g. one saved before d applied to `-t 0`) counts every pair; training stores `d` for every kernel type. Oracle for `-t 0`/`-t 1` scores and attributions: `tests/fixtures/lsgkm_wgkm_t{0,1}_*`.
- `-t 0` and `-t 2` use completely different weight table math. Do not mix.
- `score(ALT) - score(REF)` differs from deltaSVM's k-mer-weight linear approximation.
- Classic and R gkmSVM (`PREFIX_svalpha.out` + `PREFIX_svseq.fa`) record no bias and no kernel: pass the `gkmsvm_kernel` parameters (`load_classic_model`, defaults l=10 k=6 d=3 `-t 1`). Their FASTA reader drops non-ACGT letters (N is removed, not read as A), so SVs load that way. Oracle: each tool's `gkmsvm_kernel` (`benchmarks/dev/gkmsvm_fixtures.py`); `gkmsvm_classify` itself disagrees with `gkmsvm_kernel` by up to ~2%.
- `-t 4`/`-t 5` (wgkm/wgkmrbf) are the `-t 2` table (with `d`) times integer window weights from the window's distance to the sequence center: `min(M, floor(M 2^(-|W/2 - i|/H) + 1))` (`weighted._window_weights`, LS-GKM's `gkmkernel_new_object`; M 1-255 and H default to LS-GKM's 50). Not per-position weights inside the l-mer (an earlier version did that and disagreed with gkmpredict). An RC window carries its forward window's weight, so with an even window count the kernel isn't exactly RC-invariant. Oracle: `tests/fixtures/lsgkm_wgkm_*` (`benchmarks/dev/lsgkm_wgkm_fixtures.py`).
- Packed kernels take l <= 15 (`packed.MAX_L`): a uint32 holds 16 bases, and at l = 16 the all-T l-mer equals `PAD_WINDOW`. LS-GKM allows l <= 12.
- LS-GKM C is GPL v3 — cannot wrap or link against it (gkmsvm-lite is MIT).
- MLX computes in float32 (Metal has no float64), so its scores differ from CPU at the float32 level; MLX Gram tiles are normalized on the host in float64.
- Beer lab `deltasvm.pl` drops the first weight-file line as a bias header; with gkmpredict output on `nrkmers.py` l-mers that gives AAAAAAAAAA/TTTTTTTTTT raw score 0 (bias included, so -bias in a `to_deltasvm` table). Published deltaSVM scores from that script (e.g. the GkmExplain paper) include this; `dsqtl_auprc.deltasvm_pl()` reproduces it.
- The gkmexplain repo's summed deltaSVM AUPRCs (README 0.18943 / 0.18795) cover negsets 1, 3, 5 only (`combine_folds.sh` cuts the wrong columns). Five-model sums from its output files are 0.19021 / 0.18997 (`PAPER_SUM_AUPRC`). Reproduction write-up: `docs/validation.md`.
